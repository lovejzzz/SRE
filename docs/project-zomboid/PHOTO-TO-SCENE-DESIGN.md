## 1. 产品目标

用户提供一张或多张照片，AI 通过工坊搭建出可以继续编辑、进入走访、保存和分享的场景。人和 AI 使用同一套建筑规则与操作能力；还原一个新场景不需要临时修改游戏代码。

典型请求：

> “把这几张照片里的住宅搭出来。保留大落地窗、钢琴和庭院；看不到的区域补成合理布局。”

成功结果包括：完整场景文档、可编辑构件、参考视角、还原对照、推断说明及可恢复版本。不是一张看起来相似的截图，也不是只能由专用脚本生成的不可编辑地图。

**通用性的定义：在声明支持的建筑规则内，能组合出未预先设计过的场景。** 不以无限素材数或“任何建筑都能精确复原”作为承诺。

## 2. 两种还原模式

| 模式 | 优先目标 | 输入与缺失信息处理 | 交付 |
|---|---|---|---|
| Visual match | 关键视角的形体、构图、家具、材质与气氛接近参考 | 一张照片即可开始；不可见部分采用最少必要补全 | 可编辑场景、对应视角、可见部分对照、推断标记 |
| Walkable reconstruction | 房间、门、楼梯和设施形成合理可用的空间 | 多角度照片优先；尺寸或平面图可帮助校准；隐藏布局允许推断但必须记录 | 可走访的完整空间、连通检查、尺寸依据、各房间对照 |

两种模式都保留可编辑性。Visual match 不允许用面向镜头的假墙掩盖基本结构错误；Walkable reconstruction 不允许把推断的布局称为从照片中观察到的事实。

### 首版范围

- 单地块、正交墙体、多房间、多层；住宅、街角商住楼、学校和小型仓库。
- 地下室、楼梯、挑空、阳台、平屋顶与常见坡屋顶。
- 建筑外壳、室内家具、固定设备、灯饰、窗帘、桌面用品、庭院及车辆。
- 保留俯视微缩世界的辨识度，升级真实体积与统一材质光照，支持旋转观察；产品界面默认英文，存档默认本地，无多人服务器依赖。
- 照片还原默认由当前协作中的 AI 执行；普通访客可手动编辑，无需先购买或接入 AI 服务。

### 后续范围

曲线墙、任意墙角、自由层高、复杂曲面屋顶、非正交楼梯和大规模街区，需要扩展几何与渲染能力，单列后续阶段。现有贴图不能通过任意拉伸自动变成这些构件。

## 4. 用户体验与信息架构

### 4.1 从 House Library 开始

`New house` 内增加 `Blank plot` 和 `From photos`。后者打开参考工作区：导入照片、选择还原模式、可选填写一个已知尺寸，随后进入已有工坊。

不设置冗长的必填问卷。信息缺失时先完成不依赖答案的外壳和物件识别；仅在尺寸、楼层或房间连接存在影响整体布局的冲突时提出具体问题。

### 4.2 参考工作区

参考图放在可收起的右侧面板，避免与左侧素材库争抢主要操作区域。支持：

- 缩略图分组：Exterior、Living、Kitchen 等；允许手动修正 AI 分组。
- 点图放大、标注边线和对象框、指定“这两张图是同一间房”。
- 标注已知长度，显示采用的尺度及误差范围。
- 点照片中的对象，高亮场景中的对应对象；反向也成立。
- 图像与场景并排、关键点对照；仅在投影可匹配时提供透明叠图。
- `Observed`、`Inferred`、`Approximate` 图标及说明；不以颜色作为唯一区分。

新增工作区保持现有目录、楼层和建造工具的可用性；窄屏改为切换面板，不把两侧面板压到无法操作。

### 4.3 AI 建造时

显示有实际含义的阶段：`Layout → Structure → Furnish → Compare → Walkthrough`，不显示虚构的整体完成百分比。

用户可查看当前变更、暂停任务、锁定已满意对象或区域，再让 AI 继续。暂停时保留最后一个完整提交；未提交预览可丢弃。用户手动修改后，AI 必须基于新版本重新规划，不覆盖修改。

### 4.4 缺素材时

面板显示对应照片、所缺物件及当前替代方案。按顺序尝试：已有物件、已有参数变体、组合构件、制作新素材。

临时占位明确标识，不能因为“颜色大致相近”就把替代品计为完成。用户明确接受近似方案时，记录接受范围。

## 5. 建造流程

### 5.1 解析参考与建立证据

为每张照片记录房间、可能的拍摄方向、可见开口、对象、遮挡及与其他照片的关系。每个识别结论关联到图像区域，不只保留一段模型总结。

相互冲突的照片可能来自不同时间或不同房间；先保留两个解释，不将矛盾物件全部放进同一空间。

### 5.2 推断尺度与空间关系

优先使用用户给定尺寸或平面图，其次使用跨照片对应关系，最后才采用常见家具尺寸作为估计。记录每个尺度假设的来源与范围；后续尺寸修正应能更新结构，而非逐个手工挪图块。

先生成空间草图：楼层、房间、连接、墙体、门窗、楼梯和不可用空间。可见事实与隐藏区域推断分开存储。地块无法容纳时调整地块或请求解决关键尺寸冲突，不静默缩小所有家具。

### 5.3 搭建建筑结构

以大体量、楼板、外墙、内部隔墙、开口、楼梯、屋顶为顺序。先验证上下层连接和主要通路，再投入装修。

墙上安装窗户使用 `opening`，不能直接删除整段墙贴图。改变墙材质不改变开口尺寸；移动墙体不丢弃其门窗和挂件。

### 5.4 匹配与制作物件

匹配同时考虑用途、尺寸、外形、材质、安装方式和方向。优先返回可解释的候选，而非仅按名称选第一项。

对重要视觉锚点单独核对，例如大落地窗、钢琴、弧形沙发、特色楼梯；普通杂物可在结构和主要陈设确认后补充。照片里的普通摆设若没有对应游戏功能，可作为可编辑装饰，但不得标注成可使用设备。

### 5.5 对照迭代

保存场景视角，输出参考—还原对照。问题分类为：布局、比例、构图、材质、缺失物件、遮挡、光照和风格转换差异。

每次修正只作用于相关区域，保留用户锁定内容。连续修正不再改善时，保留最佳已保存版本并列出剩余差异，不能不断重排场景或降低验收要求来宣称成功。

### 5.6 走访与交付

先做结构及路径检查，再让角色实际从入口走到目标站位，执行可用设施的交互。完成后保存命名版本，保留参考视角、差异清单和构建记录。

## 6. 建筑与资产的数据模型

以下是拟新增概念，不是现有 API 或持久格式承诺。

### 6.1 Scene document v2

| 实体 | 核心信息 |
|---|---|
| Scene | 稳定ID、schemaVersion、revision、单位、地块边界、参考尺度 |
| Level | 稳定ID、相对标高、层高、楼板、洞口；地下层使用同一模型 |
| Wall edge | 稳定ID、端点、楼层、高度、厚度、内外表面材质 |
| Opening | 宿主墙ID、沿墙位置、宽高、窗台高、构件家族与状态 |
| Room | 稳定ID、用途、边界引用、楼层；拓扑推导结果与用户命名分离 |
| Object instance | 稳定ID、资产家族/版本、位置方向、参数、状态、宿主和依附对象 |
| Vertical link | 楼梯、上下平台、连接楼层、占地和净空要求 |
| Reference binding | 图片ID、图像区域、关联实体、事实/推断类型、尺寸依据 |
| View | 编辑器镜头、对照镜头、可见楼层、剖切和显示设置 |

物件渲染贴图、占地碰撞和可用空间是不同数据。细小桌面摆件不自动占据整格碰撞；一张椅子即便能放下，也需要有人能站到它旁边使用。

尺寸单位应在统一空间层转换；不能把“一个图块”未经标定就当成精确的一米。首版保留原格网作为结构精度约束，必要的尺寸误差在对照中说明。

### 6.2 资产家族

每个家族包含：稳定ID、来源版本、用途标签、尺寸、占地、安装面、锚点、已验证朝向、状态、材质变体、交互能力、所需站位和可信度依据。

必须分开三个概念：

- **方向**：同款家具的 N/W 或四向版本。
- **款式**：另一种窗框、颜色或沙发造型。
- **状态**：完好、打开、破损、玻璃移除等。

参数化采用明确支持范围。墙、楼板、玻璃段、柜体等可通过构件重复或程序几何调整；固定像素家具不进行任意非等比拉伸。参数超出范围时报告不支持，不能把明显失真的结果保存为正常资产。

### 6.3 新素材进入库的流程

参考与尺寸约束 → 制作 → 枢轴/锚点/方向设置 → 占地/碰撞/站位 → 实际放置 → 缩略图与标签 → 发布资产版本。

新图像本身不代表游戏素材已完成。缺少可用方向或安装信息的素材先进入待验收区。新增版本不静默改变已有场景中的占地、枢轴或比例；用户可以选择升级，升级可撤销。

## 7. 人与 AI 共用的操作接口

### 7.1 原则

UI 和 AI 都通过命令层修改文档。AI 不直接修改内部对象数组、localStorage、渲染数据或地图文件来绕过校验。渲染层和游戏运行层消费同一个已验证场景。

对 UI 操作、AI 请求及导入文件采用相同的支持面、边界、库存和依附规则。AI 接口不是用于偷偷放宽规则的后门。

### 7.2 拟定接口

| 接口 | 用途 |
|---|---|
| `scene.read` / `scene.inspect` | 读取版本、空间结构及指定区域，不要求每次传全库 |
| `assets.search` / `assets.describe` | 查询候选、尺寸、方向、状态及安装要求 |
| `references.read` | 在授权范围内读取参考图与标注 |
| `commands.preview` | 检查操作，返回影响对象、预览及冲突 |
| `commands.commit` | 原子提交有界操作批次，返回新版本与变化摘要 |
| `commands.undo` | 撤销指定命令或检查点后的操作，不能跨用户修改盲目回滚 |
| `scene.validate` | 返回结构、支撑、连通和交互检查结果 |
| `scene.capture` | 返回指定视角截图以及对应版本、镜头参数 |
| `walkthrough.run` | 通过角色实际控制执行有界路线和动作，返回观测证据 |
| `versions.save` / `versions.branch` | 保存阶段成果或从旧版本建立分支 |

所有修改命令具有 `requestId`、`baseRevision`、命令类型、参数和受影响实体。重复提交同一 requestId 不重复放置；版本不符返回冲突；失败整批不生效。先支持小批量，再评估大型建筑事务。

典型错误包括：`UNSUPPORTED_GEOMETRY`、`MISSING_ASSET`、`INVALID_SUPPORT`、`BLOCKED_ACCESS`、`REVISION_CONFLICT`、`STORAGE_FULL`。返回对象ID、定位和修复信息，不能只给“失败”。

### 7.3 AI 运行与网站部署

第一阶段：当前协作 AI 通过受控工具连接工坊，静态网站仍可独立运行。未连接 AI 时，From photos 仍能导入参考、标注和手动建造，明确显示自动建造尚不可用。

第二阶段如需“每位访客上传照片后自主生成”，再独立设计模型调用服务、认证、成本上限、任务队列与取消恢复。它是可选在线能力，不是本地工坊和存档的前提；模型服务密钥不能写进公开静态前端。

## 8. 视觉验证：避免虚假的相似度

真实照片通常使用透视投影，当前游戏使用固定等距投影。两者不能天然逐像素对齐。

- 游戏预览负责确认等距风格下的场景质量和可见性。
- 首版通过对应视角、关键点、轮廓、相对比例及对象清单比较，不把照片与等距截图的原始像素差当作正确性指标。
- 只有渲染系统真正具备透视相机时，才加入透视校准对照；参数不同的对照必须显示差异。
- 保存相机位置、投影、裁切、楼层、时间和灯光设置，避免用不同设置制造“改善”。

评价分别报告：关键对象与结构覆盖、尺度误差、布局与开口关系、材质/风格接近程度、推断区域和剩余差异。模型的自评分只能作为诊断线索，不能单独决定验收通过。

## 9. 可走访性验证

结构检查：共享墙一致；门窗有有效宿主；楼板与洞口一致；楼梯上下端有平台；没有悬空或越界构件。

路径检查：从入口到每个要求开放的房间及关键设施的有效站位，使用角色真实碰撞尺寸。不能只测试格子中心是否有路径。

实际走访：进门、上下楼、进入地下室、到达床边/柜前/电脑前，完成当前游戏支持的动作。保存路线、失败位置、动作结果和截图；仿真检查通过不代替实际走访。

验证模式固定角色状态，关闭与建筑验收无关的随机敌人或饥饿干扰；另外保留独立的正常游戏兼容测试。短程建筑走访不计为“三天生活”或一年生存系统验证。

## 10. 保存、迁移和参考图管理

- 采用稳定 scene ID 与 revision，区分工作草稿、保存版本和当前入住版本。
- 大场景、参考图、缩略图使用 IndexedDB；JSON/资源包导出作为可携带备份。
- 参考照片默认留在本地，不随网站代码部署或公开建筑分享自动上传。分享包默认仅含场景与必要资产依赖；包含照片是显式选项。
- v1 图块存档先无损保留，再识别可转换的结构；无法识别的图块进入 legacy layer，仍能显示与编辑。
- v2 到游戏运行数据的编译结果可重建，不能成为唯一真相；导入旧场景的转换报告列出未知项。
- 首次迁移、恢复旧版本、AI 大批次修改之前保存可恢复检查点；配额满或写入失败不覆盖最后可用版本。
- AI 与用户同时编辑时使用版本冲突检测和区域锁定；锁定冲突返回给 AI 重规划，不采用最后写入者覆盖。

## 11. 性能与操作质量目标

以下是待测目标，不是当前成绩。基准记录浏览器、设备、场景规模和测量方式。

- 连续拖动目标 60fps；代表性场景下输入到预览的 p95 不超过50ms，不依赖等待 AI 返回。
- 大规模语义查找、照片分析、全屋验证在异步任务执行；超过200ms的操作显示可取消进度。
- 素材目录保持虚拟滚动与有界缓存，不因方向合并重新挂载几万张卡片。
- 使用小、中、大三个场景规模记录长帧、内存和保存时间，最低包含2,000、10,000、50,000个实例的压力档；最大档失败时公布当前支持上限。
- 放置、拖墙、取消和撤销时不丢对象；减少动态效果设置禁用震屏，声音服从总音量。
- 所有关键操作有英文标签/tooltip、键盘路径；错误指向可见对象而非只输出内部ID。

## 12. 实施阶段与交付门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| P0 基线与规格 | 场景/资产schema、旧档清单、测试场景、尺度约定、命令协议 | 数据迁移和不可表达项明确，旧档可备份恢复 |
| P1 建筑编辑核心 | 墙/开口/房间拓扑、命令事务、多选与依附、楼层/楼梯 | 用UI完成建房、改房、复制、撤销、重载及上下楼走访 |
| P2 参考与素材工作区 | 多图管理、标注、尺度、证据关联、资产规格、缺素材流程 | 人能用该工作区按照片手动搭出一间完整房间 |
| P3 AI 垂直切片 | 查询→预览→提交→截图→修正→保存；单房间案例 | AI 无直接文件/状态写入，完成可编辑房间；人工插手后能继续 |
| P4 多层与室外泛化 | 屋顶、楼层复制、挑空、地下室、室外场地，多图空间关系 | 多栋类型实例通过结构、实际走访和版本恢复 |
| P5 未见参考验收 | 冻结版本与资产集，执行独立照片案例 | 下述盲测通过，剩余推断和近似明确披露 |

先解决结构与编辑能力，再扩大 AI 自动化。AI 若依靠绕过编辑器缺口才能搭建，说明对应工坊能力尚未完成。

每阶段先局部检查、再真实UI任务和实际走访，最后上线。文档阶段不触发部署；各阶段实施时沿用已授权的验证与发布流程。

## 13. 最终验收设计

### 13.1 两条互相独立的测试线

**固定库盲测**：冻结工坊、命令协议和资产版本，再选择未参与开发的参考照片。测试期间不得修改应用代码、直接修改场景文件或添加专为该案例准备的模板。用于证明已有系统的通用性。

**缺素材扩展测试**：专门选择一个库中没有的关键物件，只允许通过已公开的新素材接入流程补充；不得为该物件增加场景专用渲染/碰撞代码。报告制作成本及复用结果，不把它混算成固定库覆盖率。

### 13.2 场景集合

1. 单张照片的完整客厅：视觉还原、家具遮挡、桌面摆件、尺度不确定性。
2. 多图现代住宅：大窗、钢琴、庭院、车库、地下室和二楼。
3. 街角商店加楼上公寓：不同用途房间、公共/私人入口、楼层连接。
4. 两层学校：重复教室、走廊、多选复制与楼梯。
5. 小型仓库：大空间、货架、车行入口和室外装卸区。

参考输入、照片中可见事实、必需对象及验收路线在运行前固定。不能让生成代理一边搭建一边更改通过条件。

### 13.3 每例必须通过

- 所有预先标记的关键结构/对象均存在；占位和近似对象单独列出，未经接受不计通过。
- 对有可靠尺寸依据的关键长度，首版误差目标不超过一个结构格；同时报告百分比误差。若格网误差破坏必要通行或关键比例，则失败，不能用目标容差掩盖。
- 可见门窗关系和主要家具相对位置与参考一致；隐藏空间标记为推断，所有需要开放的房间可达。
- 至少一轮关键对象与布局的人工对照检查通过，记录未解决差异；不单靠代理自评分。
- 每个声明可使用的关键设施完成实际交互；不支持的行为明确列出。
- 用户能选择任一主要墙体/门窗/家具并修改；修改后的预览、存档和运行一致。
- 保存→刷新→重开→导出→导入，实体身份、位置、库存及依附关系不丢失。
- 测试一次中断恢复、一次用户手动修改后的继续构建和一次撤销恢复。
- 没有通过场景专用代码、贴图假建筑或隐藏状态注入完成任务。

另外记录：任务耗时、AI操作数、失败/重试次数、人工介入、素材命中情况和性能。先用基线实测校准成本目标，不凭空承诺几分钟完成整栋建筑。

## 14. 风险与处理

| 风险 | 处理 |
|---|---|
| 一张照片存在多种合理布局 | 保留假设与置信依据，仅补必要空间；关键冲突才询问 |
| 透视照片与等距游戏不匹配 | 结构、比例与风格分别评价，不追求错误的像素重合 |
| 错误合并素材或任意旋转贴图 | 来源可追溯、保守分组、完整方向校验；未确认关系不强并 |
| AI持续重建破坏已完成区域 | 小批次事务、区域锁定、最佳版本保存、冲突重规划 |
| 新素材漂亮但不可使用 | 安装、碰撞、站位、方向与交互共同验收 |
| 复杂场景操作变慢 | 空间索引、局部拓扑更新、虚拟目录和异步检查；记录性能上限 |
| 引擎无法表达参考几何 | 明确近似或延期扩展，不通过隐藏特例假装支持 |
